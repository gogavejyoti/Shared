# Feature Development: Excel-Like Multi-Level Row and Column Grouping in Luckysheet

## 1. Objective

Implement an advanced Row and Column Grouping functionality in the existing Luckysheet-based spreadsheet application, similar to Microsoft Excel's Outline and Grouping functionality.

The implementation must support:
- Multi-level row grouping.
- Multi-level column grouping.
- Nested row and column groups.
- Expand and collapse functionality.
- Excel-style outline levels.
- Dynamic grouping and ungrouping.
- Preservation of existing spreadsheet data, formulas, formatting, and other Luckysheet features.

The objective is to provide an Excel-like user experience without breaking the existing Luckysheet functionality.

## 2. First Step: Understand the Existing Architecture

Before writing any code, thoroughly analyze the existing application.

Understand the following:

1. Existing Luckysheet version and source structure.
2. How Luckysheet is initialized and configured.
3. How rows and columns are internally represented.
4. How row heights and column widths are maintained.
5. How hidden rows and columns are handled.
6. How sheet data, formulas, and formatting are stored.
7. How scrolling and frozen panes work.
8. How toolbar actions and context menus are implemented.
9. How spreadsheet state is saved and restored.
10. How existing custom plugins and extensions interact with Luckysheet.

Identify the appropriate integration points before implementation.

**Important:** Do not immediately start modifying the Luckysheet core. First evaluate whether the functionality can be implemented through existing APIs or a separate extension/plugin architecture.

## 3. Row Grouping Functionality

Implement row grouping similar to Microsoft Excel.

### 3.1 Basic Row Grouping

Users should be able to:

- Select one or multiple consecutive rows.
- Right-click and select Group Rows.
- Use a toolbar grouping option.
- Collapse the selected rows.
- Expand the selected rows.

Example:

Before grouping:

| Row | Employee | Department |
|---|---|---|
| 1 | John | IT |
| 2 | David | IT |
| 3 | Michael | IT |
| 4 | Sarah | HR |
| 5 | Peter | HR |

After grouping rows 1–3:

- Display an outline indicator.
- Show a minus (-) button to collapse the group.
- Clicking minus hides the grouped rows.
- Show a plus (+) button to expand the group.

### 3.2 Multi-Level Nested Row Grouping

Support multiple levels of grouping, similar to Excel's outline levels.

Example:

Level 1: Department

- IT
  - Level 2: Team A
    - Employee 1
    - Employee 2
  - Level 2: Team B
    - Employee 3
    - Employee 4
- HR
  - Level 2: Recruitment
    - Employee 5
    - Employee 6

Expected behavior:

- Users can independently expand and collapse each nested group.
- Collapsing a parent group must hide all its child groups.
- Expanding a parent group must respect the previous collapsed state of child groups.
- Expanding or collapsing a child must not affect unrelated groups.
- Support at least 8 outline levels, subject to the existing architecture.

### 3.3 Row Grouping Controls

Implement Excel-like controls:

- Plus (+): Expand group.
- Minus (-): Collapse group.
- Outline level buttons: 1, 2, 3, etc.
- Level 1 displays only the highest-level summary.
- Higher levels progressively reveal nested details.
- A button to expand all groups.
- A button to collapse all groups.

Position the outline controls along the left row-header area, similar to Excel.

## 4. Column Grouping Functionality

Implement equivalent functionality for columns.

### 4.1 Basic Column Grouping

Users should be able to:

- Select consecutive columns.
- Group selected columns.
- Ungroup selected columns.
- Expand and collapse grouped columns.

Display Excel-like outline indicators above the column headers.

### 4.2 Multi-Level Nested Column Grouping

Example:

| Employee Details | | | Performance | | |
|---|---|---|---|---|---|
| Name | Department | Designation | Q1 | Q2 | Q3 |

Possible grouping:

- Level 1: Employee Details
  - Level 2: Personal Information
  - Level 2: Employment Information
- Level 1: Performance
  - Level 2: Quarterly Results

Expected behavior:

- Nested column groups.
- Independent expand/collapse.
- Multiple outline levels.
- Correct column positioning after collapsing.
- Maintain column widths and formatting.

## 5. Grouping and Ungrouping Operations

Implement the following operations:

### Group
- Create a group from selected rows or columns.
- Support nested grouping.
- Validate overlapping or conflicting group definitions.
- Automatically determine the correct outline level.

### Ungroup
- Remove the selected group's definition.
- Preserve the underlying row and column data.
- Avoid accidentally removing parent or child groups.
- Support ungrouping individual nested levels.

### Clear Outline
- Remove all grouping definitions.
- Restore all hidden rows and columns associated with grouping.
- Preserve manually hidden rows and columns.

## 6. Expand and Collapse Behavior

This is one of the most important parts of the implementation.

Implement a reliable state-management mechanism.

Each group should maintain:

- Unique group ID.
- Group type (row or column).
- Start index.
- End index.
- Outline level.
- Parent group ID.
- Child group IDs.
- Expanded/collapsed state.
- Summary position.
- Creation metadata.

Example conceptual structure:

```javascript
{
  groups: [
    {
      id: "row-group-1",
      type: "row",
      start: 2,
      end: 10,
      level: 1,
      parentId: null,
      collapsed: false,
      children: ["row-group-2"]
    },
    {
      id: "row-group-2",
      type: "row",
      start: 4,
      end: 7,
      level: 2,
      parentId: "row-group-1",
      collapsed: false,
      children: []
    }
  ]
}
```

This is a conceptual example. Design the final data model based on the existing Luckysheet architecture.

## 8. Technical Implementation Requirements

### 8.1 Architecture

Prefer a modular implementation.

Suggested modules:

```text
luckysheet/
  plugins/
    grouping/
      groupingManager.js
      rowGrouping.js
      columnGrouping.js
      groupingRenderer.js
      groupingEvents.js
      groupingState.js
      groupingUtils.js
      groupingPersistence.js
```

Adjust the structure based on the existing application.

Responsibilities:

- `groupingManager.js`: Central grouping controller.
- `rowGrouping.js`: Row-specific grouping operations.
- `columnGrouping.js`: Column-specific grouping operations.
- `groupingRenderer.js`: Render outline indicators and controls.
- `groupingEvents.js`: Handle expand/collapse and user interactions.
- `groupingState.js`: Maintain grouping state.
- `groupingUtils.js`: Group validation and hierarchy calculations.
- `groupingPersistence.js`: Save and restore grouping definitions.

### 8.2 Rendering

Ensure:

- Outline indicators render correctly.
- No unnecessary full-sheet re-rendering.
- Expand/collapse operations are efficient.
- Row heights and column widths remain unchanged.
- Scroll position is maintained.
- Frozen rows and columns work correctly.
- Indicators remain aligned during scrolling.
- No flickering during expand/collapse.

### 8.3 Data Integrity

Grouping must never:

- Delete spreadsheet data.
- Modify cell values.
- Change formulas.
- Modify cell formatting.
- Change merged-cell definitions.
- Corrupt row heights or column widths.
- Break filters, sorting, or other spreadsheet functionality.

Use the existing hidden-row/hidden-column mechanisms where appropriate, but distinguish grouping-based visibility from manually hidden rows and columns.

## 9. Dynamic Operations

Grouping must remain correct when users:

- Insert rows inside a group.
- Delete rows inside a group.
- Insert columns inside a group.
- Delete columns inside a group.
- Move or copy cells.
- Sort data.
- Apply filters.
- Undo and redo operations.

Update group indexes and hierarchy when structural changes occur.

Avoid relying on static row or column indexes that become invalid after spreadsheet modifications.

## 10. Persistence

Grouping definitions must survive:

- Spreadsheet save.
- Spreadsheet reload.
- Browser refresh.
- Sheet switching.
- Workbook reopening.

Store grouping metadata separately from cell values where possible.

Ensure backward compatibility with existing saved spreadsheets that do not contain grouping metadata.

Do not modify the existing spreadsheet storage format unnecessarily.

## 11. Performance Requirements

The application may contain large spreadsheets with thousands of rows and hundreds of columns.

Optimize the implementation for:

- Large datasets.
- Multiple nested groups.
- Frequent expand/collapse operations.
- Multiple worksheets.
- Large numbers of grouping definitions.

Avoid unnecessary recalculation and full-sheet rendering.

Use efficient group lookup and visibility calculations.

## 12. Undo and Redo

Integrate grouping operations with the existing undo/redo mechanism.

The following operations should be reversible:

- Create group.
- Remove group.
- Expand group.
- Collapse group.
- Expand all.
- Collapse all.
- Clear outline.

Undoing a grouping operation must restore the previous grouping state accurately.

## 15. Important Development Rules

1. Do not rewrite the existing Luckysheet engine.
2. Do not replace Luckysheet with another spreadsheet library.
3. Do not break existing functionality.
4. Do not implement a visual-only grouping mechanism.
5. Grouping must work with actual spreadsheet data and visibility.
6. Do not use CSS display:none as the sole mechanism for hiding spreadsheet rows or columns.
7. Maintain compatibility with existing Luckysheet APIs wherever possible.
8. Keep the implementation modular and maintainable.
9. Avoid unnecessary modifications to core source files.
10. Do not remove existing custom plugins or application-specific functionality.

If modifications to the Luckysheet core are unavoidable, explain why, identify the exact files and functions affected, and isolate the changes.

## 17. Final Acceptance Criteria

The feature will be considered complete only when:

- Users can group rows and columns independently.
- Users can create multiple levels of nested groups.
- Users can expand and collapse individual groups.
- Users can expand and collapse all groups.
- Excel-like outline level controls work.
- Parent-child group relationships are maintained.
- Grouping survives save and reload.
- Undo/redo works correctly.
- Existing spreadsheet features continue working.
- Large datasets perform efficiently.
- No existing application functionality is broken.

**Final Instruction:** Work incrementally. First analyze the existing codebase and present the architecture findings and implementation plan. Do not start modifying files until the analysis is complete. After that, implement one phase at a time, test each phase, and provide a summary of changed files and test results before proceeding to the next phase.
